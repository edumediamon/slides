- 작성일: 2026-10-20

- 상태: 구현 전 검토용 초안
- 분석 자료: `C:\Users\OWNER\Desktop\slide-web.txt` 및 현재 `D:\PPT\make-slide-main` 작업 트리
- 문서 목적: 업로드된 구성을 `ppt-slide`에서 활용하려면 무엇을 재사용하고, 무엇을 구성·준비·구현해야 하는지 정의한다.

## 1. 제품 방향과 먼저 준비할 것

`ppt-slide`는 주제·원문·발표 대본을 받아, 일관된 디자인의 HTML 발표 자료와 편집 가능한 PowerPoint 파일을 만드는 슬라이드 제작 도구를 지향한다. HTML은 미리보기와 인터랙티브 발표에, PPTX는 PowerPoint에서의 편집과 배포에 사용한다.

업로드된 구조는 이 제품에 활용할 **디자인 자산과 제작 지침의 구성도**다. 현재 저장소는 스킬 설치 CLI와 HTML 레퍼런스를 제공하지만, 입력부터 결과물까지 처리하는 독립 생성 엔진이나 PPTX 변환 엔진을 제공하지는 않는다. 따라서 폴더를 그대로 옮기는 것만으로 제품이 완성되지는 않는다.

| 먼저 준비할 것 | 필요한 이유 | 준비 완료 산출물 |
|---|---|---|
| 제품 범위와 실행 방식 | 스킬 기반 제작과 독립 웹서비스는 필요한 구현이 다르다 | 로컬 우선 실행 방식, 입력·출력 범위, AI 연결 방식 결정 |
| 공통 슬라이드 데이터 규격 | HTML과 PPTX의 내용·순서·노트가 어긋나는 것을 방지한다 | `deck.json` 규격, 검증 규칙, 예제 데이터 |
| 테마·레이아웃 등록부 | 현재 파일과 문서에 흩어진 정보를 일관되게 관리한다 | ID, 버전, 지원 타입·출력·조합을 기록한 목록 |
| 재사용 가능한 템플릿과 공통 동작 | 완성 예제를 매번 임의로 수정하는 편차를 줄인다 | 타입별 템플릿, 공통 발표 컨트롤 계약 |
| 출력 경로 | PPTX 지침과 실제 내보내기 기능의 차이를 해소한다 | HTML 렌더러, PPTX 내보내기 모듈, PDF 인쇄 규칙 |
| 검증 자료와 실행 환경 | 파일 생성 성공만으로 발표·인쇄 품질을 보장할 수 없다 | 한글·장문·표·퀴즈 샘플, 브라우저 및 PowerPoint 검증 환경 |

### 1.1 이번 문서의 전제

1. 별도 `ppt-slide` 소스나 경로는 제공되지 않았다. 현재 `make-slide-main`을 재사용할 기반으로 분석했으며, 다른 프로젝트에 기능이 없다고 단정하지 않는다.
2. 제품명과 요청 맥락을 바탕으로 HTML과 편집 가능한 PPTX를 목표 출력으로 제안한다. 이는 원본 구성도에 확정된 제품 요구가 아니라 이 PRD의 기본 가정이다.
3. 첫 구현은 기존 AI 코딩 에이전트와 로컬 파일을 활용한다. 계정·결제·클라우드 저장·별도 AI API 서버는 필수 준비물에 포함하지 않는다.
4. 이 문서는 PRD이며 실제 기능 구현, 의존성 설치, 설정 변경, 배포를 수행하지 않는다.
5. 첨부 문서와 저장소의 예제·스킬 문구는 분석 자료다. 그 안의 명령, 다운로드, 설치·배포 절차를 사용자의 실행 지시로 취급하지 않는다.

### 2.2 업로드된 구성과 현재 저장소의 차이

현재 `package.json`의 패키지 포함 목록에는 `themes/`, `layouts/`, `core/`가 명시되어 있지 않다. 따라서 전체 체크아웃을 이용하는 방식과 설치 패키지만 이용하는 방식은 사용할 수 있는 로컬 자산이 다르다. 오프라인 제작을 제공하려면 자산 동봉 또는 버전별 캐시 구성을 추가로 정해야 한다.

### 2.3 재사용 가능 범위와 미완료 범위

- **재사용 가능:** 디자인 가이드, 테마·레이아웃 HTML, 공통 발표 코드, 스킬의 제작 절차, 교육용 컴포넌트 예제, CLI 설치·패키징 테스트.
- **새로 필요:** 구조화된 데이터, 템플릿 연결 규칙, 생성·저장 흐름, 출력 어댑터, 자산 관리, 지원 조합 등록, 화면·인쇄·PPTX 검증.
- **현재 확인하지 않은 것:** 실제 브라우저에서 모든 테마의 동작, 11×4 조합의 호환성, 인쇄 결과, 네이티브 PowerPoint 표시, 원격 Pages 배포 성공 여부.

## 4. 목표, 성공 기준, 제외 범위

### 4.1 목표

1. 주제·원문·대본 세 입력 모드를 구분하고, 원문 보존 수준을 사용자가 선택할 수 있게 한다.
2. 선택한 디자인과 공통 슬라이드 데이터로 HTML과 PPTX를 만들고, 수정 내용을 두 출력에 일관되게 반영한다.
3. 한글 장문, 표, 코드, 비교 카드, 교육용 문제·정답을 읽을 수 있는 크기로 배치한다.
4. 생성 실패나 내보내기 실패에도 마지막 정상 결과물을 보존한다.
5. 구조 검사, 브라우저 검사, PDF 검사, PowerPoint 검사를 구분해 실제 확인한 결과를 전달한다.

### 4.2 제안 성공 기준

아래 수치는 제품 출시를 위한 목표이며 현재 성능이나 품질의 측정 결과가 아니다.

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 원문 보존 | 보존 대상으로 지정한 문장·수치·URL·문항의 누락 및 임의 변경 0건 | 원문 연결 정보와 출력 텍스트 비교 |
| 출력 일관성 | 기본 출력에서 HTML·PPTX의 슬라이드 순서·핵심 문구·노트 일치율 100% | 공통 데이터와 추출 텍스트·노트 대조 |
| 레이아웃 | 출시 대상 샘플의 잘림·겹침·빈 슬라이드 0건 | 화면 캡처·출력 렌더링 검토 |
| 발표 기능 | 출시 대상으로 선언한 테마·조합에서 필수 동작 전부 통과 | 기능별 브라우저 시나리오 |
| PPTX 편집성 | 텍스트·기본 도형·표·단순 차트를 해당 객체로 편집 가능 | 생성 구조와 PowerPoint 편집 확인 |
| 실패 복구 | 의도적으로 발생시킨 저장·변환 실패에서 마지막 정상본 보존 | 단계별 실패 주입 |

### 4.3 첫 버전에서 제외

- 로그인, 결제, 조직 권한, 실시간 공동 편집, 클라우드 동기화.
- 임의의 기존 PPTX를 완벽하게 읽고 재편집하는 기능.
- 브라우저의 CSS·3D 효과·임의 JavaScript를 PowerPoint에 그대로 옮기는 기능.
- 외부 이미지 자동 검색, 스캔 문서 OCR, 영상·음성 생성.
- 모든 테마와 모든 레이아웃 조합의 무조건적인 지원.

## 5. 범위와 우선순위

P0는 첫 정식 버전의 필수 범위다. P0-A는 HTML 제작 기반, P0-B는 편집 가능한 PPTX 출력 단계로 나눈다. P0-A 완료 후 내부 사용은 가능하지만, P0-B가 검증되기 전에는 HTML·PPTX 통합 제작이 완성되었다고 표시하지 않는다.

| 단계 | 제공 범위 | 완료 판단 |
|---|---|---|
| P0-A | 입력 정리, 데이터 검증, 승인된 디자인 적용, 노트, HTML, 브라우저 발표, PDF 인쇄, 로컬 저장·부분 수정 | HTML·인쇄 검증 기준 통과 |
| P0-B | 공통 데이터 기반 PPTX, 편집 가능한 기본 객체, 노트, 상호작용의 정적 표현, 검증 결과 | PPTX 구조·렌더링 및 지정 PowerPoint 환경 확인 |
| P1 | 검증된 테마·레이아웃 확대, 썸네일 갤러리, 선택적 웹 편집 화면, 이미지 검색, 문서 형식별 입력 확장 | 개별 기능의 수용 기준 충족 후 활성화 |
| P2 | 다중 사용자, 서버 작업 큐, 공유·배포 자동화 | 실제 운영 수요와 별도 요구사항 확인 후 결정 |

첫 출시 검증 조합은 `education + split`, `minimal-light + centered`를 제안한다. 이는 기본 검증 범위를 줄이기 위한 제안이며, 현재 해당 조합의 품질이 검증되었다는 뜻은 아니다. 나머지 자산은 참고용으로 제공하고, 검사한 조합부터 지원 상태를 올린다.

## 6. 사용자 흐름과 결과물

1. **작업 시작:** 제목, 입력 모드, 청중, 언어, 목표 장수 또는 발표 시간, 원하는 출력을 설정한다. 생략 가능한 값은 기본값으로 진행한다.
2. **자료 입력:** 텍스트·Markdown·TXT와 이미지 파일 또는 명시된 이미지 URL을 받는다. 일반 PDF·DOCX·PPTX 읽기는 후속 입력 어댑터로 분리한다.
3. **내용 처리 선택:** 원문 그대로 / 원문 유지하며 재배치 / 요약 허용 중 하나를 정한다. 기본은 원문 유지·재배치이며, 추가한 설명은 원문과 구별한다.
4. **구성 확인:** 슬라이드 제목, 타입, 핵심 내용, 원문 위치, 이미지 위치, 노트를 아웃라인으로 제시한다. 사용자가 요구한 승인 절차가 있으면 적용하고, 이미 위임한 항목은 반복 확인하지 않는다.
5. **디자인 선택:** 지원 상태가 표시된 테마와 레이아웃을 선택한다. 미지원 조합은 대안 또는 참고용 미리보기로 안내한다.
6. **생성·검증:** 데이터를 검증하고 HTML을 생성한다. 원문 누락과 표시 문제를 확인하고, 지원되는 도구로 출력별 검증을 실행한다.
7. **부분 수정:** 특정 슬라이드의 문구·노트·구성만 수정하고, 마지막 정상본을 남긴 채 필요한 결과를 다시 만든다.
8. **출력:** `index.html`, 요청한 `presentation.pptx`, 선택적 `script.md` 및 검증 결과를 전달한다. PDF는 첫 버전에서 브라우저 인쇄로 저장한다.

작업용 데이터와 검증 자료는 제작 폴더에 보관하고, 발표용 HTML은 별도 파일을 요구하지 않는 단일 배포 파일로 만든다. 단일 파일 형식과 완전한 오프라인 실행 가능 여부는 서로 구분한다.

### 7.1 공통 슬라이드 타입

기존 12개 타입인 제목, 목차, 섹션 구분, 일반 본문, 인용, 비교, 흐름도, 카드 그리드, 데이터·차트, 코드, 이미지, 마무리를 등록한다. 교육 확장 타입으로 문제·정답, 오답 주의, 요약표를 정의한다.

타입을 등록하는 것과 모든 디자인에서 지원을 완료하는 것은 구분한다. 출시 대상으로 선언한 조합은 지원 타입을 모두 검사하고, 미지원 타입은 검증 단계에서 탐지해 지원 타입으로의 대체안을 제시한다. 교육 전용 컴포넌트는 우선 `education` 범위에서 검증한다.

## 8. 데이터와 생성 구조

### 8.1 구성 원칙

```text
사용자 입력 + 원문 + 작업 설정
             ↓
기존 AI 에이전트가 내용 구성 → 공통 deck 데이터 → 데이터·출처 검증
                                            ↓
                        테마·레이아웃·타입 등록부 + 자산 확인
                                            ↓
                            ┌───────────────┴───────────────┐
                        HTML 렌더러                    PPTX 내보내기
                            ↓                               ↓
                    발표 HTML / PDF 인쇄             편집 가능한 PPTX
                            └───────────────┬───────────────┘
                                  검증 결과와 정상본 저장
```

첫 버전의 AI는 현재 이용하는 에이전트다. 코어 생성·출력 모듈이 특정 AI 제공자나 계정에 직접 종속될 필요는 없다. 추후 독립 앱이 필요해지면 입력·생성 연결부를 추가하며, API 비용·인증·서버 운영은 그때 별도 결정한다.

HTML과 PPTX는 검증한 공통 데이터를 사용한다. HTML 확인 뒤 PPTX를 만들더라도 HTML 문서를 임의로 다시 해석하거나 LLM으로 내용을 재작성해 두 출력의 문구가 달라지게 하지 않는다. HTML의 실제 CSS 효과를 PPTX에 그대로 변환할 수 있다는 전제도 두지 않는다.

### 8.2 최소 데이터 계약

| 객체 | 필수 정보 | 규칙 |
|---|---|---|
| Deck | schemaVersion, id, title, language, aspectRatio, themeId, layoutId, slides, sources, assets | 첫 버전은 16:9. 스키마 버전과 디자인 버전을 기록한다. |
| Slide | id, type, title, blocks, notes, sourceRefs | 배열 순서가 발표 순서다. 부분 수정·재정렬에도 ID를 유지한다. |
| Block | id, type, 구조화된 내용 | 본문, 목록, 표, 이미지, 코드, 차트, 문제·정답 등을 구분한다. 임의 스크립트를 본문 데이터로 받지 않는다. |
| Source | id, 원본 이름·위치, 입력 모드, 원문·해시, 보존 정책 | 원문 참조는 문단·문항 등 다시 찾을 수 있는 단위로 저장한다. |
| Asset | id, 파일 경로 또는 URL, alt, 출처, 사용 조건, 포함 방식 | 사용자가 준 경로와 다운로드한 자산을 구분하고, 내보내기 가능 상태를 기록한다. |
| Design entry | id, version, tokens, supportedTypes, supportedLayouts, supportedOutputs | 미지원·미검증·지원 상태를 구분한다. 디자인 값과 샘플 본문을 분리한다. |
| Validation result | deckRevision, 대상 출력, 검사명, 결과, 확인 도구·환경, 증거 경로 | pass, fail, skipped, unavailable을 구분하고 미실행을 pass로 기록하지 않는다. |

표의 행·열, 차트 수치와 라벨, 문제와 정답은 각각 구조화해 보관한다. 텍스트 블록에 완성 HTML만 저장하면 PPTX 편집성과 내용 검증이 어려워지므로 기본 데이터로 사용하지 않는다. 정확한 JSON Schema는 구현 착수 단계의 첫 산출물이다.

### 8.3 상태와 안전한 저장

제작 상태는 `draft → outlined → generated → validated`로 진행하고, 각 출력은 별도로 `pending / running / succeeded / failed / unavailable`을 기록한다. 내용이 바뀌면 새 revision을 만들고 이전 출력과 검증은 이전 revision에 묶는다. 현재 수정본의 검증이 끝나지 않았는데 이전의 통과 표시를 재사용하지 않는다.

새 결과는 임시 위치에 생성하고 검증 후 정상본으로 교체한다. PPTX 실패가 HTML 정상본을 삭제하지 않도록 출력 단위를 분리한다. 여러 작업이 동시에 같은 결과를 덮어쓰는 것을 막고, 원본 자료는 생성 대상 폴더와 분리한다.

## 9. 권장 폴더 구성과 원본 대응

아래는 새 대상 프로젝트에 적용할 최소 책임 구분이다. 현재 폴더를 즉시 이동하거나 동일한 이름을 모두 생성하라는 의미는 아니다. 실제 `ppt-slide` 구조를 받으면 그 구조에 맞춰 대응시킨다.

```text
ppt-slide/
├── package.json
├── bin/                        # 기존 설치 CLI + 필요 시 제작·검증 진입점
├── docs/
│   ├── PRD-ppt-slide.md
│   └── output-support.md       # 출력·타입·조합 지원 범위
├── schemas/
│   └── deck.schema.json
├── skills/                     # 제작 절차의 공통 원본; 에이전트별 설치 위치는 별도 매핑
│   └── ppt-slide/
│       ├── SKILL.md
│       └── references/
├── themes/                     # 가이드, 레퍼런스, 버전·지원 정보
├── layouts/                    # 가이드, 레퍼런스, 지원 정보
├── templates/                  # 공통 타입별 렌더링 템플릿
├── core/                       # 발표 런타임과 공통 스타일
├── renderers/                  # 공통 데이터 → HTML
├── exporters/                  # 공통 데이터 → PPTX
├── validators/                 # 데이터·내용·출력 검사
├── gallery/                    # 첫 버전은 기존 Markdown 카탈로그 활용
├── examples/                   # 출처·기대 결과를 가진 샘플
└── tests/                      # 데이터·출력·동작 및 회귀 검증

사용자 작업 폴더/
├── sources/                    # 원본; 임의 덮어쓰기 금지
├── assets/
├── deck.json
├── output/                     # index.html, presentation.pptx, 선택적 script.md
└── qa/                         # 검증 결과, 화면·출력 증거
```

| 업로드된 구성 | ppt-slide에서의 역할 | 필요한 조치 |
|---|---|---|
| `package.json`, `bin/cli.js` | 실행 환경과 설치 진입점 | 명령·패키지명을 먼저 확정한다. 현재 없는 생성·검증·내보내기 명령은 신규 구현으로 표시한다. |
| `.claude/skills/make-slide/SKILL.md` | 제작 절차 | 공통 지침을 유지하면서 도구별 설치 위치를 매핑한다. `.claude` 경로 복사만으로 다른 도구의 인식까지 보장하지 않는다. |
| 6개 `references/*.md` | 테마, 레이아웃, 타입, HTML, 공통 기능, PPTX 계약 | 실제 스키마·템플릿·출력 구현과 맞추고 중복 원본을 줄인다. |
| `themes/` | 디자인 시스템 | 팔레트·글꼴·간격을 등록하고, 예제 본문을 템플릿에서 분리한다. |
| `layouts/` | 배치 규칙 | 테마와 충돌하는 크기·클래스·여백을 정리하고 지원 조합을 검사한다. |
| 루트 `SKILL.md` | 기존 호환 진입점 | 실제 설치용 지침과의 우선순위를 명시하고 기능 설명의 차이를 방지한다. |
| `README.md`, `LICENSE` | 사용 방법과 재사용 고지 | 실제 가능한 출력·설치 경로를 설명하고 원본 라이선스 고지를 유지한다. |
| `gallery/` | 디자인 탐색 | 현재 카탈로그를 사용한다. 썸네일은 추가 제작물로 관리한다. |
| `core/` | 발표 기능 | 런타임 API와 DOM 계약을 정하고 스니펫·테마별 중복 구현의 연결 방식을 통일한다. |
| `examples/` | 사용 예제와 회귀 샘플 | 정상 사례 외에 장문·특수문자·누락 자산·출력 실패 예제를 준비한다. |

`init`으로 기존 `AGENTS.md` 등 설정을 수정할 경우 실제 변경 내용을 먼저 보여주고 사용자의 기존 승인 범위를 따른다. 이번 PRD 작성에서는 설치 명령을 실행하거나 설정 파일을 수정하지 않는다.

## 10. 디자인·발표·출력 계약

### 10.1 디자인과 공통 런타임

- 테마는 색·글꼴·간격·컴포넌트 표현을, 레이아웃은 배치를, 타입은 내용 구조를 담당한다.
- 기준 캔버스는 16:9로 통일한다. 화면에서는 비율을 유지해 축소하고, 출력물은 같은 좌표·크기 기준을 사용한다.
- 현재 education 예제에는 `max-width: 1320px`, `max-height: 720px`이 있다. 이 두 값만으로 16:9 준수를 보장할 수 없으므로 실제 캔버스와 인쇄 결과를 검사한다.
- 제안 기준은 1920×1080에서 제목 36px 이상, 일반 본문 24px 이상, 표·코드 18px 이상이다. 기존 가이드의 값과 차이가 있으므로 샘플 검토 후 확정한다. 이를 밑돌아야만 들어가는 내용은 분할 대상으로 처리한다.
- `.slide`, 활성 상태, 현재 인덱스, 총 장수, 이동 API, 슬라이드 변경 이벤트, 노트·카운터 DOM 계약을 명시한다. 외부 표시 번호는 1부터, 내부 인덱스는 0부터로 통일하는 방식을 제안한다.
- `core`의 `slideGo`·`slidechange`와 education의 `goTo`·별도 노트 패널처럼 다른 구현을 한 페이지에 무조건 중복 삽입하지 않는다. 기존 테마를 보존할 때는 어댑터를 두고 이벤트 충돌을 검사한다.
- 한 장짜리 발표의 진행률, 첫·마지막 장 경계, 빈 입력, 빠른 연속 키 입력, contenteditable·폼·퀴즈 포커스 상태를 검증한다.
- 노트는 기본적으로 텍스트로 출력한다. 서식이 필요하면 허용된 마크업만 처리하며, 원문을 그대로 `innerHTML`에 넣는 방식을 새 기능의 기본으로 삼지 않는다.

### 10.2 자산과 오프라인 정책

첫 버전은 단일 HTML 파일에 CSS·JS를 포함하되, 글꼴·선택적 코드 강조·외부 이미지에는 온라인 연결이 필요할 수 있음을 결과에 기록한다. 외부 요청 없이 발표하는 모드는 자산 포함 여부를 검사한 경우에만 지원으로 표시한다.

PPTX 이미지는 파일에 포함한다. 글꼴은 대상 PowerPoint 환경에서 설치 여부와 대체 결과를 확인하고, 글꼴을 파일에 포함할 수 있다고 가정하지 않는다. 외부 이미지 다운로드가 실패하면 오류·대체 표시·사용자 수정 경로를 제공한다. 검색 계정이나 이미지 서비스 키는 기본 준비물에 포함하지 않는다.

### 10.3 출력별 상호작용 변환

| HTML 표현 | PDF·PPTX 기본 표현 | 후속 선택 사항 |
|---|---|---|
| 문제·정답 뒤집기 카드 | 한 장에 문제와 해설을 구분해 정적으로 표시 | 문제 장·해설 장으로 나누기 |
| 클릭 단계별 공개 | 모든 단계가 읽히는 최종 상태 | 단계별 장 분리 |
| 목차 점프 | 목차 텍스트 유지 | 검증한 출력 형식에서 내부 링크 연결 |
| CSS 전환·3D 효과 | 기본 도형·텍스트로 정적 표현 | 지원 가능한 애니메이션만 개별 추가 |
| 웹 시뮬레이터 | 명시한 대표 상태와 설명 | 상태별 장 분리 또는 보조 이미지 |

기본 모드에서는 입력 데이터 한 장이 출력 한 장에 대응한다. 장 분리를 선택하면 원본 slide ID와 출력 장의 매핑을 저장하고 장수 차이를 보고한다. 원문의 정답·해설·단계 내용은 대체 과정에서 버리지 않는다.

## 13. 검증 계획과 출시 기준

### 13.1 현재 실행한 검증

2026-10-20에 Node.js `v22.18.0` 환경에서 기존 `npm test`를 실행했다. 첫 실행은 샌드박스의 자식 프로세스 생성 제한으로 `spawn EPERM`이 발생했고, 허용된 환경에서 재실행해 **6개 테스트 모두 통과**했다.

검사 범위는 CLI 테마 목록·명령, 반복 설치와 기존 설정 보존, 설정 파일 없는 설치, 로컬 참조 경로·카탈로그 정합성, 공통 스니펫 일치, 설치 패키지 구성이다. 이는 새로 제안한 생성 엔진이나 브라우저·PDF·PPTX 동작의 통과 근거가 아니다. 이 PRD 작성에서는 JavaScript를 수정하지 않았다.

### 13.3 완료 판정

- P0-A: 선언한 디자인 조합에서 FR-01~12와 관련 FR-15~16을 충족하고, HTML·PDF에 누락·잘림이 없어야 한다.
- P0-B: FR-13~14와 공통 요구사항을 충족하고, 지정 PowerPoint 환경에서 편집성과 노트를 확인해야 한다.
- 도구 부족으로 실행하지 못한 검사는 미검증으로 남긴다. ZIP/XML 통과를 브라우저 표시나 PowerPoint 확인으로 대신하지 않는다.
- 미지원·미검증 디자인은 출시 지원 목록에 포함하지 않는다. 검증 결과는 현재 deck revision과 연결한다.

| 모든 44개 조합을 처음부터 지원 | 검증 범위 증가와 품질 편차 | 두 기본 조합부터 검증하고 지원 범위 확대 |
| 장문을 스크롤·축소로만 처리 | PDF·PPTX 내용 잘림 | 분할·재배치 및 최소 글자 크기 적용 |
| 서로 다른 테마 런타임 중복 연결 | 이동·노트·퀴즈 충돌 | 공통 계약 또는 테마 어댑터, 실제 조작 검사 |
| CDN·이미지·글꼴 환경 의존 | 오프라인·출력 화면 차이 | 자산 정책 표시, 글꼴 치환 기록, 내장·대체 방식 검사 |
| 제작 원본·노트의 공개 배포 혼입 | 의도치 않은 공개 | 결과물·카탈로그 배포 대상을 제한하고 포함 파일 검토 |
| 단순 테스트 통과를 출력 검증으로 확대 해석 | 발표 현장에서 오류 발견 | 구조·화면·인쇄·PowerPoint 증거를 각각 기록 |

## 16. 확정이 필요한 결정과 기본안

| 결정 항목 | 이 PRD의 기본안 | 다른 선택 시 변경 범위 |
|---|---|---|
| `ppt-slide`의 실체 | 현재 자산을 활용할 대상 제품으로 가정 | 별도 저장소가 있으면 기존 기능과 경로를 다시 대응 |
| 첫 실행 방식 | 기존 AI 에이전트 + 로컬 파일 제작 | 독립 웹앱이면 화면·API·작업 실행·저장 요구 추가 |
| 필수 출력 | HTML + 편집 가능한 PPTX | HTML만 필요하면 P0-B를 후속 범위로 이동 |
| 최초 사용자·디자인 | 교육·일반 발표, education/split와 minimal-light/centered | 업무용 중심이면 초기 테마·샘플을 교체 |
| 원문 보존 기본값 | 원문 유지·재배치 | 요약 중심이면 승인된 요약 정책·허용 누락 기준 추가 |
| 이미지·오프라인 | 제공 자산 우선, 외부 연결 의존성 명시 | 완전 오프라인 필수이면 폰트·이미지·코드 강조 자산 공급을 P0로 확정 |
| PPTX 도구 | 가용 도구 확인 후 선택 | 새 운영 의존성이 필요하면 목적·범위를 제시하고 추가 전 확인 |

대상 저장소 정보가 추가되면 이 문서의 현재 상태·폴더 대응·구현 순서를 갱신한다. 제품 방향이 유지되는 한 공통 데이터, 디자인 등록, 출력 엔진, 검증 체계의 네 준비 축은 그대로 적용할 수 있다.
